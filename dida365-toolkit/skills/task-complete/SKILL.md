# 完成滴答清单任务

把一个或多个任务标记为已完成：查找 → 确认 → 逐项完成 → 回执。

通道选择、工具命名发现、能力发现协议、批量结果与部分失败、安全边界与失败分类统一见 `${CLAUDE_PLUGIN_ROOT}/references/tool-conventions.md`；使用任何滴答清单能力之前先读该文件，本文只补充完成流程。状态取值与语义见该文件第 7 节。

## 接入前提

- **凭据来源**：MCP 通道固定使用默认凭据文件 `~/.dida365/token`；环境变量 `DIDA365_API_TOKEN` 是**可选且优先**的来源，只对本地/API 直接调用生效，不能替代默认凭据文件（原因与排查见 `tool-conventions.md` 第 8 节与 setup-guide）。
- 缺少凭据或调用返回 401/403 时，说明原因并转入 setup-guide；不自动切换通道或认证方式，也不在本 skill 里改配置。
- 调用失败按 `tool-conventions.md` 第 9 节分类处置；超时或结果不确定时先只读核验现状，不自动重试、不换通道重做。

## 步骤

### Step 1: 查找要完成的任务

**用户已给出明确的任务 ID 与所属清单时，跳过查找，直接进入 Step 3 执行（沿用原骨架）**：这两项信息本身已是用户明确的指令，不必再让用户重复确认；批量场景同样只需按用户已给出的目标逐项执行。

只给了描述时（如"把买菜那个任务完成"）先查找：查看当前连接实际暴露的工具与 schema（清单列表、清单详情、条件筛选、单任务读取等），按语义选择；工具名与参数以发现结果为准——插件模式下形如 `mcp__plugin_dida365-toolkit_dida365__<tool>`，OAuth 手动配置模式下命名空间可能不同，**不得凭记忆拼工具名，也不得写死唯一前缀**。

- 已知所属清单 → 读取该清单的任务；不确定在哪个清单 → 先列出清单，必要时单独读取 inbox（清单列表分页且不含虚拟 inbox，按分页继续跟页）。
- 命中多个相近任务时**展示候选**（标题、清单、截止日、状态，必要时附任务 ID），让用户选定要完成哪一项；不自行挑选，也不在确认前对"最像的那个"执行完成操作。
- 没有匹配时如实说明查了哪些清单，以及可能未覆盖的部分。

### Step 2: 向用户确认

展示目标任务信息（标题、清单、优先级、截止日，必要时附任务 ID），**得到用户确认后**再执行完成操作。批量场景一次列出全部目标项，说明要完成的是哪几项。

### Step 3: 逐项执行完成

用 MCP 的完成能力把任务标记为已完成（`status` 为 `2` = 已完成；**不要用 `completedTime` 判断状态**，见 `tool-conventions.md` 第 7 节）。逐个任务执行，**不假设存在批量接口或批次原子性**；批量场景下逐项执行并保留每项的目标标识，便于逐项核对结果。

### Step 4: 逐项反馈与回执

按 `tool-conventions.md` 第 6 节处理批量结果：**逐项反馈**每一项是成功、失败、结果未知还是尚未提交，不把部分成功写成整批成功，也不仅凭工具未抛错就推断每项都成功。

- **失败与未知按部分失败规则处理**：返回缺少逐项结果、部分响应或中途超时且无法确认整体效果时，相关项归入结果未知；先通过只读查询核验现状，不凭相似标题猜测，也不自动重放整批或重放已确认成功的项。
- 核验后给出回执：哪些已确认完成（必要时附完成时间）、哪些失败或结果未知、下一步建议（如重新确认后只补做未生效且用户允许的项）。
- 不新增事务、恢复状态库或重试引擎；上述规则属于编排与反馈契约。

## 边界

- **本 skill 只做"完成"**：放弃任务（不做了/取消）与恢复已放弃任务转 task-crud；不要在本 skill 里用状态更新替代完成能力。
- **已完成任务的恢复能力需实测确认**：把已完成任务改回未完成是否可行、有无副作用，**以实测结果为准，需实测确认**；不要向用户断言"不可恢复"，也不要断言"必定可恢复"。
- **不要用 `completedTime` 判断是否完成**：实测放弃也会写入该时间，恢复为未完成时不保证清除；以 `status` 为准。
- 平台消歧：与 mstodo 等其他待办工具并存、本轮未指明平台且上下文无法确定时，先向用户确认平台再执行。

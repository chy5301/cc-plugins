# 移动和整理滴答清单任务

在项目（清单）之间移动任务：明确任务与源/目标清单 → 查真实 ID → 预演与确认 → 用官方移动能力执行 → 逐项反馈。

通道选择、工具命名发现、能力发现协议、批量结果与部分失败、安全边界与失败分类统一见 `${CLAUDE_PLUGIN_ROOT}/references/tool-conventions.md`；使用任何滴答清单能力之前先读该文件，本文只补充移动与整理的工作流细节。官方端点来源与已验证限制见 `${CLAUDE_PLUGIN_ROOT}/references/api-reference.md`。

## 接入前提

- **默认 Bearer 接入**：仅插件 `headersHelper` 模式要求默认凭据文件 `~/.dida365/token`；环境变量 `DIDA365_API_TOKEN` 是**可选且优先**的本地/API 来源，不能替代该模式的默认凭据文件（见 `tool-conventions.md` 第 8 节与 setup-guide）。
- **已有 OAuth MCP 接入**：已认证且可用的手动 OAuth MCP 不需要个人 Token 或默认凭据文件，直接使用当前连接的工具；不因文件缺失转入 setup-guide，也不要求运行 Token helper 自检。
- **API 补缺**：只有确认 MCP 缺口、需要正式调用 API 时才要求个人 Token；缺少时说明限制，由用户选择补配或在滴答应用中完成，不读取 OAuth 缓存，不改动现有 OAuth MCP。
- 没有可用 MCP 接入或调用返回 401 时，说明原因并按当前认证方式转入 setup-guide；403 按权限问题处理。不自动切换通道或认证方式，也不在本 skill 里改配置。
- 调用失败按 `tool-conventions.md` 第 9 节分类处置；超时或结果不确定时先只读核验现状，不自动重试、不换通道重做。

## 移动使用官方移动能力

- **用官方移动工具，不用"复制后删除"模拟**：复制会丢失原任务的 ID 与创建时间、可能连带子任务与关联信息，还会留下重复项；移动只改归属，不重建任务。
- 调用前先查看当前连接实际暴露的工具与 schema，按语义选择（清单列表、清单详情、任务读取、移动任务等）。工具名与参数以发现结果为准——插件模式下形如 `mcp__plugin_dida365-toolkit_dida365__<tool>`，OAuth 手动配置模式下命名空间可能不同；**不得凭记忆拼工具名，也不得写死唯一前缀**。
- 只有 MCP 明确缺少所需工具或必需参数时，才按 `tool-conventions.md` 第 2 节的能力发现协议走 API 补缺路径；调用报错不算缺口。
- 移动不改变任务的其他属性（标题、优先级、日期、标签等）；移动后要改这些属性，转 task-crud。

## 步骤

### Step 1: 明确任务与源/目标清单

确认三件事，缺哪件就问哪件，不猜、不擅自代填：

- 要移动哪些任务（标题或任务 ID）？
- 从哪个清单移出（源清单）？
- 移到哪个清单（目标清单）？

批量场景一次列出全部「任务 → 源清单 → 目标清单」组合。目标清单不确定时先列出清单让用户选择；存在同名或近似名清单时展示候选（名称与 ID）让用户确认，不按列表顺序自行挑一个。

### Step 2: 查真实 ID

移动需要**真实的清单 ID 与任务 ID**，不能凭名称直接执行：

1. 取清单列表，核对源清单与目标清单的身份（同名清单先确认）。清单列表是分页的，按分页继续跟页；清单列表**不含虚拟 inbox**，需要时单独读取 inbox（见 `${CLAUDE_PLUGIN_ROOT}/references/api-reference.md` 已验证限制）。
2. 读取源清单下的任务，按标题/内容匹配后**展示候选**（标题、清单、截止日、状态，必要时附任务 ID），让用户确认要移动的是哪几项；**确认之前不要对"最像的那个"执行移动**。
3. 记录每项的「任务 ID + 源清单 ID + 目标清单 ID」作为执行前保留的目标标识，便于执行后逐项核对（`tool-conventions.md` 第 6 节）。
4. 命中多个相近任务时不自行挑选；没有匹配时如实说明查了哪些清单，以及可能未覆盖的部分。

### Step 3: 预演与确认

移动会改变任务归属，执行前先向用户**预演**这一次操作：

- 逐项列出将要移动的任务（标题 + ID）、源清单与目标清单，说明一共几项。
- 预演是本地构造与展示，不等于服务端验证。若本次需要走 API 补缺，先按 `tool-conventions.md` 第 2 节用 `--dry-run` 展示方法、路径与请求体（不含凭据），确认无误后再正式执行。
- 得到用户**确认**后再进入 Step 4；批量场景一次列出全部目标项并整体确认，用户没有明确同意时不执行。

### Step 4: 逐项执行移动

用官方移动能力逐项移动，保留 Step 2 记录的每项目标标识。**不假设存在批量接口或批次原子性**；批量场景逐项执行、逐项记录实际结果，不把一次调用或一次未抛错当作整批成功的根据。

### Step 5: 逐项反馈与回执

按 `tool-conventions.md` 第 6 节处理批量结果：**逐项反馈**每一项是成功、失败、结果未知还是尚未提交，不把部分成功写成整批成功。

- **失败与未知按部分失败规则处理**：返回缺少逐项结果、部分响应或中途超时且无法确认整体效果时，相关项归入结果未知；先通过只读查询确认任务的当前归属，不凭相似标题猜测，也不自动重放整批或重放已确认成功的项。
- **读回核验的状态判据**：`status` 取值为 `-1`/`0`/`2`（已放弃/未完成/已完成），**不要用 `completedTime` 判断状态**——实测放弃也会写入该时间，恢复为未完成时不保证清除（见 `tool-conventions.md` 第 7 节）。
- 核验后给出回执：哪些已确认移动（必要时附当前所在清单）、哪些失败或结果未知、下一步建议（按原授权范围或重新确认后的范围，只补做未生效且用户允许的项）。
- 不新增事务、恢复状态库或重试引擎；上述规则属于编排与反馈契约。

## 注意事项

- **按当前工具能力编排**：一次移动多少项、能否跨源清单，**以当前发现到的 schema 与实际返回为准**，不沿用旧实现的批次约束。
- **移动 ≠ 修改**：移动只改归属；任务标题、优先级、日期、标签等由 task-crud 修改，完成走 task-complete。
- **平台消歧**：与 mstodo 等其他待办工具并存、用户未指明平台、且上下文无法确定时，先向用户确认平台再执行。

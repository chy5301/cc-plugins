# 滴答清单任务管理

对滴答清单中的任务进行创建、查看、更新、删除、放弃与恢复操作。本 skill 覆盖"标记完成"以外的写操作；完成任务走 task-complete。

通道选择、工具命名发现、能力发现协议、批量结果与部分失败、安全边界与失败分类统一见 `${CLAUDE_PLUGIN_ROOT}/references/tool-conventions.md`；使用任何滴答清单能力之前先读该文件，本文只补充任务 CRUD 的工作流细节。状态取值与语义见该文件第 7 节，官方端点来源与已验证限制见 `${CLAUDE_PLUGIN_ROOT}/references/api-reference.md`。

## 接入前提

- **凭据来源**：MCP 通道固定使用默认凭据文件 `~/.dida365/token`；环境变量 `DIDA365_API_TOKEN` 是**可选且优先**的来源，只对本地/API 直接调用生效，不能替代默认凭据文件（原因与排查见 `tool-conventions.md` 第 8 节与 setup-guide）。
- 缺少凭据或调用返回 401/403 时，说明原因并转入 setup-guide；不自动切换通道或认证方式，也不在本 skill 里改配置。
- 调用失败按 `tool-conventions.md` 第 9 节分类处置；超时或结果不确定时先只读核验现状，不自动重试、不换通道重做。

## 工具发现

写操作默认走 `.mcp.json` 注册的 `dida365` 服务。调用前先查看当前连接实际暴露的工具与 schema，按语义选择（创建任务、读取任务、更新任务、删除任务、清单列表、清单详情等）。工具名与参数以发现结果为准——插件模式下形如 `mcp__plugin_dida365-toolkit_dida365__<tool>`，OAuth 手动配置模式下命名空间可能不同；**不得凭记忆拼工具名，也不得写死唯一前缀**。

只有 MCP 明确缺少所需工具或必需参数时，才按 `tool-conventions.md` 第 2 节的能力发现协议走 API 补缺路径；调用报错不算缺口。

## 状态语义：未完成、已完成、已放弃

任务的 `status` 取值与含义统一见 `tool-conventions.md` 第 7 节：`-1`=已放弃、`0`=未完成、`2`=已完成；子任务的完成值是 `1`，与任务的取值不是一套，**不要把子任务的 `1` 当成任务的"已放弃"**。

- **不要用 `completedTime` 判断状态**：实测放弃也会写入该时间，恢复为未完成时不保证清除（见 `tool-conventions.md` 第 7 节）；以 `status` 为准。
- **完成**（`2`）：走 task-complete 的专用完成能力，不要用本 skill 的状态更新冒充完成。
- **放弃**（`-1`）：用户说"不做了/取消这个任务"时，把任务标为已放弃。
- **恢复**（`0`）：把已放弃的任务改回未完成。

### 放弃与恢复需单独说明

schema 允许传 `-1`/`0`，**不等于业务效果已被保证**：放弃与恢复属于需要单独验收的语义，不能仅凭"字段可以传值"就向用户断言"已放弃""已恢复"。实际效果（是否真正改回未完成、是否残留完成时间）**需实测确认**。执行后读回核验 `status`，并按实际观察到的值回执；核验不到时如实报告结果未知。

## 创建任务

必需信息：**标题**与**目标清单**；字段定义以当前发现到的 schema 为准。优先级 `0`=无、`1`=低、`3`=中、`5`=高。

- **缺信息先追问**：标题或目标清单缺失时不猜、不擅自代填，先请用户补齐；目标清单不确定时先列出清单让用户选择。
- **同名清单要确认**：存在同名或近似名清单时展示候选（名称与 ID）让用户确认，不按列表顺序自行挑一个。
- **日期写完整 ISO 8601 并带明确时区**（如 `2026-04-05T14:30:00+0800`）：本次迁移不再承诺短日期会被转换。
- 创建成功后向用户展示返回的任务详情（标题、清单、ID、日期）作为回执。

## 查看与定位任务

- 用户已给出清单与任务 ID 时直接读取该任务。
- **只知道描述时先查找再确认**：读取候选清单（含 inbox）的任务，按标题/内容匹配后**展示候选**（标题、清单、截止日、状态，必要时附任务 ID），让用户确认目标；**确认之前不要对"最像的那个"执行任何写操作**。
- 匹配到多个相近任务时不自行挑选；没有匹配时如实说明查了哪些清单、以及可能未覆盖的部分。
- 清单列表是分页的且不含虚拟 inbox，按分页继续跟页；需要时单独读取 inbox。

## 更新任务

- 只提交用户要求修改的字段，不整对象覆盖；缺信息先追问。
- **批量修改**：先确认目标项集合再逐项执行；逐项反馈成功、失败、结果未知与尚未提交，未知项先只读核验、不整批重放，按 `tool-conventions.md` 第 6 节的部分失败规则处理。批量操作没有原子性保证，不把部分成功写成整批成功。

## 删除任务

- **删除不可逆**：执行前先展示目标任务（标题、清单、必要时附任务 ID），说明将删除哪一项，**得到用户确认后再执行**。
- 命中多个任务、或删除影响不明确（如可能牵连子任务）时，逐项列出并分别确认。
- 若某次删除需走 API 补缺，先按 `tool-conventions.md` 第 2 节用 `--dry-run` 展示请求概要（不含凭据），确认后再正式执行。
- 删除后读回核验（重新读取该任务或在清单中确认已不存在）并报告实际结果；无法核验时如实说明结果未知，不自动重试。

## 工作流建议

1. 信息完整（标题 + 清单）直接创建；信息不完整先追问。
2. 只给描述时：查找 → 展示候选 → 确认 → 再执行写操作。
3. 创建/更新成功后展示返回详情作为回执。
4. 删除前展示任务信息再确认，删除后读回核验。
5. 完成走 task-complete；放弃/恢复在本 skill 分流；批量写操作按部分失败规则逐项反馈。
